# Implementation plan

Everything you need to build, in the order you should build it, with the specific things that
will go wrong.

---

## 1. Repository structure

The documents you are reading live in `project/distilled/`. The **code** repository you build
is separate and looks like this:

```text
duqa/                          ← your repo (call it whatever you like)
│
├── README.md                  what this is, how to reproduce every number in one command
├── requirements.txt           five packages
│
├── data/                      generated by prepare_data.py — small, committed
│   ├── corpus.jsonl           {"id": int, "text": str}   ~13,000–15,000 lines
│   ├── queries.jsonl          {"qid": str, "text": str, "split": "dev"|"test"}
│   ├── qrels.json             {"qid": [gold corpus ids]}
│   ├── train_pairs.tsv        anchor \t positive          ~17,000–20,000 lines
│   └── stats.json             corpus size, pair count, leakage-check result
│
├── src/
│   ├── prepare_data.py        dataset → corpus, qrels, queries, training pairs
│   ├── train.py               fine-tune MiniLM with MultipleNegativesRankingLoss
│   ├── evaluate.py            rank the corpus, compute Recall@10 / MRR@10
│   └── utils.py               seeding, encoding helper, the two metrics
│
├── experiments/
│   └── run_all.sh             one command → every number in the report
│
├── results/
│   ├── metrics.json           every run, every split, every seed
│   ├── main_table.md          the three-system table
│   ├── ablation_table.md      batch size 16 / 32 / 64
│   ├── error_analysis.md      20 failure cases + what you concluded
│   └── figures/               bar chart + line chart
│
└── report/
    └── report.md              5–7 pages
```

**Four Python files. Total ~500 lines.** If you find yourself creating a fifth, you are
over-engineering — put it in `utils.py`.

### What each file actually does

| File | Input | Output | Roughly |
|---|---|---|---|
| `prepare_data.py` | the HuggingFace dataset id | `data/*` | 80 lines |
| `train.py` | `data/train_pairs.tsv` + CLI args | `runs/<name>/` (a saved `SentenceTransformer`) | 70 lines |
| `evaluate.py` | `data/corpus.jsonl`, `data/qrels.json`, `data/queries.jsonl`, a model name **or** a path | `results/metrics.json` (appended) + per-query rankings | 120 lines |
| `utils.py` | — | seeding, `encode()`, `recall_at_k()`, `mrr_at_k()`, jsonl loading | 80 lines |

Note `evaluate.py` takes **either** a HuggingFace model name (for the zero-shot baseline) **or**
a local path (for your fine-tuned checkpoints). That single design choice means the baseline and
the fine-tuned system go through *literally the same code*, which is what makes the comparison
controlled.

## 3. Implementation steps

### Step 0 — Environment (30 min)

* Open a Colab notebook, set runtime → GPU (T4 is free and sufficient).
* `!nvidia-smi` to confirm you have a GPU.
* `pip install -r requirements.txt`.
* Verify: `SentenceTransformer('all-MiniLM-L6-v2').encode(["hello world"]).shape == (1, 384)`.

### Step 1 — `prepare_data.py` (half a day)

```python
from datasets import load_dataset
ds = load_dataset("sentence-transformers/askubuntu")
# ds['train']   12745 rows
# ds['dev']       200 rows
# ds['test']      200 rows
# each row: {'query': str, 'positive': [str, ...], 'negative': [str, ...]}
```

Then:

1. **Build the corpus.** `corpus_texts = sorted(set(all queries) | set(all positives))`.
   Print `len(corpus_texts)` — expect ~13,000–15,000. Map each text to an integer id.
   *(Deliberately excluding the `negative` lists keeps the corpus size predictable; the other
   ~13,000 real questions are already enough distractors.)*
2. **Build the queries.** The 200 dev + 200 test `query` fields, with ids `"dev-0" … "test-199"`
   and their split recorded.
3. **Build the qrels.** For each eval query, `qrels[qid] = [corpus_id_of(p) for p in row['positive']]`.
   Assert every positive text is in the corpus (if not, you built the corpus wrong).
   Print the mean number of gold duplicates per query — expect ~1–2.
4. **Build the training pairs.** For each **train** row, one `(query, p)` pair per `p` in
   `row['positive']`. Print the count — expect ~17,000–20,000.
5. **Leakage check.** Assert that no train anchor or train positive text appears among the 400
   dev/test query texts. Print `PASS` or `FAIL`. **If it fails, stop and think** — you are about
   to train on your test set.
6. Write `corpus.jsonl`, `queries.jsonl`, `qrels.json`, `train_pairs.tsv`, `stats.json`.

### Step 2 — `utils.py` (1 hour)

* `set_seed(s)` — `random`, `numpy`, `torch`, and `torch.cuda`.
* `load_jsonl`, `load_json`.
* `encode(model, texts, batch_size=256)` → `np.ndarray [n, 384]`, **L2-normalised**
  (`normalize_embeddings=True`).
* `recall_at_k(ranked_ids, gold_ids, k)` → `|gold ∩ top-k| / |gold|`.
* `mrr_at_k(ranked_ids, gold_ids, k)` → `1/rank` of the first gold, else 0.
* `retrieve(query_vec, corpus_matrix, exclude_ids=None, k=10)` →
  `scores = corpus_matrix @ query_vec` (already normalised, so this *is* cosine), then mask
  `exclude_ids`, then `np.argpartition`.

### Step 3 — `evaluate.py` (half a day)

```text
for each system:
    if system == "bm25":      scores come from rank_bm25 over tokenised corpus
    else:                     encode corpus once, encode queries, dot product
    for each eval query:
        mask the query's own corpus id          ← critical, see checkpoint 4
        take top-10
        accumulate Recall@10 and MRR@10
    write results/metrics.json
    also dump per-query top-10 for the error analysis
```

Two details that matter:
* **Encode the corpus once per model and cache it to `results/embeddings-<name>.npy`.** 15,000
  short texts is seconds, but you will re-run evaluation ~10 times.
* **Mask the query's own document.** The eval queries are themselves corpus documents (they are
  dataset rows). Without masking, every query retrieves itself at rank 1 with score 1.0 and every
  metric reads ~100%.

### Step 4 — Baselines, before any training (half a day)

```bash
python src/evaluate.py --system bm25            --split dev
python src/evaluate.py --system bm25            --split test
python src/evaluate.py --system all-MiniLM-L6-v2 --split dev
python src/evaluate.py --system all-MiniLM-L6-v2 --split test
```

You now have rows B1 and B2 of the main table. **Do not proceed until these numbers survive all
ten debugging checkpoints in §6.**

### Step 5 — `train.py` (one day)

```python
from sentence_transformers import (SentenceTransformer, SentenceTransformerTrainer,
                                   SentenceTransformerTrainingArguments, losses)
from datasets import Dataset

model = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2")

train_ds = Dataset.from_dict({
    "anchor":   [...],   # from data/train_pairs.tsv
    "positive": [...],
})

loss = losses.MultipleNegativesRankingLoss(model)     # scale=20 → τ=0.05, the default

args = SentenceTransformerTrainingArguments(
    output_dir=f"runs/e{epochs}-b{batch}-s{seed}",
    num_train_epochs=epochs,
    per_device_train_batch_size=batch,
    learning_rate=2e-5,
    warmup_ratio=0.1,
    seed=seed,
    fp16=True,                       # T4 only; drop it locally if it errors
    save_strategy="no",
    logging_steps=50,
)

trainer = SentenceTransformerTrainer(model=model, args=args,
                                     train_dataset=train_ds, loss=loss)
trainer.train()
model.save(f"runs/e{epochs}-b{batch}-s{seed}/final")
```

Flags: `--epochs`, `--batch-size`, `--lr`, `--seed`, `--out`. That's it.

Optional one-liner, if the API cooperates: `batch_sampler=BatchSamplers.NO_DUPLICATES` in
`SentenceTransformerTrainingArguments`. Give it 20 minutes; if it errors, drop it.

### Step 6 — First training run (2 hours including debugging)

```bash
python src/train.py --epochs 3 --batch-size 32 --lr 2e-5 --seed 42 --out runs/e3-b32-s42
python src/evaluate.py --system runs/e3-b32-s42/final --split dev
```

Expected wall-clock: **minutes**, not hours. ~19,000 pairs ÷ 32 ≈ 600 steps/epoch × 3 epochs.
If a run takes more than ~30 minutes on a T4, something is wrong (usually `max_seq_length`
padded to 256 for 12-token questions — check your tokenisation, or set `max_seq_length=128`).

### Step 7 — The experiments (week 3)

```bash
# model selection on dev: which epoch count?
for e in 1 2 3; do
  python src/train.py --epochs $e --batch-size 32 --lr 2e-5 --seed 42 --out runs/e$e-b32-s42
  python src/evaluate.py --system runs/e$e-b32-s42/final --split dev
done

# three seeds at the chosen epoch count
for s in 13 42 1337; do
  python src/train.py --epochs $E --batch-size 32 --lr 2e-5 --seed $s --out runs/e$E-b32-s$s
  python src/evaluate.py --system runs/e$E-b32-s$s/final --split test
done

# the one ablation: batch size = number of in-batch negatives
for b in 16 64; do
  python src/train.py --epochs $E --batch-size $b --lr 2e-5 --seed 42 --out runs/e$E-b$b-s42
  python src/evaluate.py --system runs/e$E-b$b-s42/final --split dev
done
```

Nine runs, minutes each. Put all of it in `experiments/run_all.sh` so the whole thing is one
command.

### Step 8 — Error analysis (week 3, one afternoon)

From the per-query dump, print the 20 test queries where the fine-tuned model's MRR@10 is worst.
For each, write one row: query text, the gold duplicate's text, what ranked #1 instead, and one
of these labels:

| Label | Meaning |
|---|---|
| **vocabulary mismatch** | gold shares almost no content words with the query |
| **over-specific query** | query has hardware/version details the gold lacks |
| **plausible-but-wrong neighbour** | the top-1 is about the same topic but is a different question |
| **unlabelled duplicate** | the #1 result looks like a genuine duplicate that was never marked |
| **annotation error** | the marked "duplicate" is not really a duplicate |

The count in the **unlabelled duplicate** row is the number that turns your error analysis into
a finding: it is a direct, manual estimate of the 95%-incompleteness that
[Lei et al.](https://aclanthology.org/N16-1153/) measured.

## 5. Reproducibility rules (cheap, do all five)

1. `set_seed(seed)` at the top of `train.py`, from the CLI flag.
2. Save every run's full arg set next to the model (`runs/<name>/args.json`).
3. Never overwrite an output file — write `results/metrics.json` by appending with a run id.
4. Commit `data/` (it is small) so the corpus and splits are frozen.
5. `experiments/run_all.sh` must reproduce every number in the report from a clean checkout.

## 6. Debugging checkpoints — run all ten in week 1

Each of these catches a specific silent failure. The first four are cheap; the last six catch
the errors that actually ruin projects.

| # | Check | Passes when | Catches |
|---|---|---|---|
| 1 | Print 5 random rows of each split | you see real Ubuntu questions, and `dev`/`test` have 200 rows | loading the wrong dataset or split |
| 2 | `len(corpus)` ≈ 13,000–15,000; `len(qrels[qid])` ≥ 1 for all 400 queries | both true | broken dedupe or broken text→id mapping |
| 3 | **Leakage check:** no train anchor or train positive appears among the 400 eval query texts | zero overlaps | training on your test set |
| 4 | **Self-exclusion:** for each eval query, the top-1 result is not the query's own text | 0 / 400 self-matches | **the #1 silent killer** — metrics inflated to ~100% |
| 5 | Zero-shot MiniLM Recall@10 is well above chance but far from 100% | roughly 30–75% | chance level (≈ 10/15000 ≈ 0.07%) means broken qrels; >95% means checkpoint 4 failed |
| 6 | BM25 Recall@10 is non-trivial | > 10% | ≈0 means broken tokenisation or corpus/qrels mismatch |
| 7 | Training loss starts near `ln(batch_size)` (= 3.47 for batch 32) and falls within ~100 steps | both true | wrong loss, wrong data format, or lr wildly off. `ln(N)` is the exact expected value for a uniform softmax, so this is a precise check. |
| 8 | After training: mean cosine of held-out **positive** pairs went **up**; mean cosine of **random** pairs stayed near 0 | both true | **representation collapse** — if every cosine ≈ 1, the model mapped everything to one point |
| 9 | Cross-check your Recall@10 against `sentence_transformers.evaluation.InformationRetrievalEvaluator` on one configuration | the two numbers agree to ~0.5 pt | a bug in your own metric code |
| 10 | Same seed twice → identical metrics to 4 decimal places | yes | non-determinism that will make your 3-seed spread meaningless |

**Checkpoint 7 is the one nobody does and everybody should.** The initial value of
`MultipleNegativesRankingLoss` is `ln(N)` — that is not a rule of thumb, it is what the formula
gives when all similarities are equal. If your first logged loss is 3.47 at batch 32, your loss
is wired correctly. If it is 0.0 or 12.0, stop before you waste a day.

## 8. Colab notes

* Runtime → Change runtime type → T4 GPU. Free tier is enough for this entire project.
* Mount Drive or re-clone each session; **save your `runs/` and `results/` outside the
  notebook**, because Colab will disconnect and take your RAM disk with it.
* `fp16=True` on T4. If you get a dtype error, drop it — the project is small enough to run in fp32.
* Keep `data/` in the repo (a few MB). Do not re-download and re-derive the corpus every session;
  a re-derivation with a different set ordering will silently change your corpus ids.
* Put the dataset download in `prepare_data.py` with a local cache check so re-runs are instant.

## 9. If you are behind schedule

Cut in this order. Never cut anything above the line you have reached.

1. Drop the batch-size ablation (saves 2 runs, ~1 day).
2. Drop the third seed (report 2 seeds instead of 3).
3. Drop the error analysis to 10 queries instead of 20.
4. Drop the second figure.
5. Drop the dev split from the tables (report test only).

**Never cut:** the leakage check, the self-exclusion check, the BM25 baseline, or the zero-shot
control. Those four things are what make the number mean something.
