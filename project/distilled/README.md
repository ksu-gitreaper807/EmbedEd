# Distilled project — the smallest version that is still worth doing

**A 4-week, 2nd-year CSE project on contrastive learning for domain-specific embeddings.**

This folder is a *rewrite*, not a summary. The previous specification
([`distilled-project/`](../../distilled-project)) was a good research design and a bad 4-week plan:
five negative-sampling strategies, 457K documents, FAISS, cross-domain evaluation, bootstrap
statistics. Everything in it was defensible. Almost none of it is necessary to answer the question.

Read [`PROJECT_SPEC.md`](PROJECT_SPEC.md) first, then [`SCOPE.md`](SCOPE.md).

---

## What the project does

You take a small pretrained sentence encoder that knows *general* English, teach it what
"the same question" means in one narrow technical domain (Ubuntu/Linux support questions),
and measure whether that teaching actually helped.

That is it. One dataset, one model, one loss, one experiment.

---

## Why it matters

Off-the-shelf embedding models are trained on general text. When you use them in a technical
domain — bug reports, support forums, lab notebooks — the word "similar" means something
narrower than it does on the open web. Two Ubuntu questions can be duplicates while sharing
almost no content words ("*how do I get sound working after upgrading?*" / "*no audio since
13.10 update*").

The interesting part is that **the literature does not promise this works**. Domain adaptation
of sentence embeddings is established as a *technique*
([TSDAE](https://aclanthology.org/2021.findings-emnlp.59/),
[GPL](https://aclanthology.org/2022.naacl-main.168/)),
but on duplicate-*detection* tasks specifically, several studies report that fine-tuning buys
little or nothing, and that a keyword baseline (BM25) is hard to beat
([BEIR](https://arxiv.org/abs/2104.08663): "BM25 is a robust baseline";
[Jiang et al., JSS 2023](https://doi.org/10.1016/j.jss.2023.111607): deep models lose to IR).
So a *negative* result is a real result here, not a failure. That is what makes this a research
project rather than a tutorial.

---

## Research question (one sentence)

> **Does contrastive fine-tuning on 19,000 in-domain duplicate-question pairs improve duplicate
> retrieval over the same encoder used off-the-shelf, and does it beat a keyword baseline?**

Three systems, one test set, two numbers. Everything else is commentary.

## The pipeline you will build and be able to explain

```text
text                      "how do i fix a 404 error when updating packages ?"
  ↓  tokenizer            split into word pieces, add [CLS]/[SEP]
pretrained encoder        6-layer MiniLM, 23M params — reads the sentence, produces one
  ↓  mean pooling          vector per token; average them (masking padding)
embedding                 a 384-d list of numbers; L2-normalised → a direction
  ↓  cosine similarity    two directions → one number in [-1, 1]; the whole "semantic
                          similarity" idea reduces to this dot product
contrastive loss          "among the 32 candidates in this batch, your duplicate must rank
  ↓  (InfoNCE)            highest"; the other 31 are negatives, obtained for free
fine-tuned embedding      backprop through the encoder; the 384-d space is re-warped so
                          that Ubuntu duplicates point the same way
```

Every arrow is one function call you will write or one library call you will read. Nothing else
is in the model.

## The experiment

| System | What it is | What it tells you |
|---|---|---|
| **B1 — BM25** | keyword matching, no neural network, ~15 lines | the "do we need a neural model at all?" floor |
| **B2 — MiniLM, zero-shot** | `all-MiniLM-L6-v2`, no training, cosine ranking | **the control.** The only difference from B3 is the fine-tuning |
| **B3 — MiniLM, contrastively fine-tuned** | B2 + 3 epochs of MultipleNegativesRankingLoss on in-domain duplicate pairs | the thing you are measuring |

All three rank the same ~15,000-question corpus for the same 400 held-out queries.

**Primary metric:** Recall@10 — of the duplicate questions that exist, how many appear in the top 10?
**Secondary metric:** MRR@10 — how high is the first correct one, averaged?

Both are computed by ~15 lines of numpy. No nDCG, no MAP, no bootstrap, no FAISS.

## Stop condition — read this twice

> **The project is finished when BM25, zero-shot MiniLM, and one contrastively fine-tuned
> MiniLM have each been evaluated on the fixed test split, and their Recall@10 and MRR@10
> numbers are in one table.**

Everything after that is optional. If it is day 26 and you have that table, stop running
experiments and start writing.

**What is never allowed to happen:** adding a fourth system because the third one was boring,
adding a metric because the numbers moved the wrong way, or adding a dataset because the
effect size was small. Those are scope-creep reflexes, and [`SCOPE.md`](SCOPE.md) exists to
make them feel like what they are.

## Final sanity check (answered honestly)

| Check | Answer |
|---|---|
| Can one student implement the core system in ~2 weeks? | **Yes.** ~500 lines across 4 files, all of it standard `sentence-transformers` usage. |
| Can the other 2 weeks go to experiments and writing? | **Yes.** A 3-epoch run is minutes, so weeks 3–4 are mostly *reading output*. |
| Does it run on one consumer GPU / Colab? | **Yes.** 23M params, ~15K corpus, no FAISS. A free T4 is plenty. |
| Can the student understand every major component? | **Yes.** Tokenizer → encoder → mean pool → cosine → InfoNCE. Five ideas, no shortcuts. |
| Is there exactly one main research question? | **Yes.** "Does in-domain contrastive fine-tuning help?" |
| Is there exactly one primary model? | **Yes.** `all-MiniLM-L6-v2`. |
| Is there exactly one primary training objective? | **Yes.** `MultipleNegativesRankingLoss`. |
| Is there a simple baseline? | **Yes, two.** BM25 and the *untrained* version of your own model. |
| Is there a clear evaluation? | **Yes.** Recall@10 + MRR@10 on a fixed 200-query test split. |
| Is it complete with every optional extension removed? | **Yes.** See Version A in [`SCOPE.md`](SCOPE.md). |

## One honest warning

The single most common way this project fails is **not** that the model does not learn. It is
that the student reports a number from a broken evaluation harness and builds four weeks of
conclusions on it. Symptom: the fine-tuned model improves by 30 points, or BM25 scores 0.4%,
or every query retrieves itself at rank 1.

`IMPLEMENTATION_PLAN.md` has ten numbered debugging checkpoints. **Run all ten in week 1.**
They take two hours and they are the difference between a project and a story.
